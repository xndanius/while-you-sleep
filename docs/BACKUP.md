# W3 cloud backup

The GitHub-hosted backup is scheduled for **Monday, 12 October 2026 at 19:31 Europe/Vilnius**, targeting the 20:00 W3 deadline. GitHub supports an IANA timezone on a schedule; scheduled jobs can be delayed or dropped under heavy load, so **Actions → Record the W3 cloud backup → Run workflow → main → Run workflow** is the same manual retry. Active cron definitions do not prove unattended runs: the backup requires real scheduled evidence. Cron has no year field: the workflow's calendar gate skips every later scheduled date. [GitHub schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Before opening Chromium, the workflow reads the actual public feed, machine JSON, public GitHub commit history and GitHub's metadata for scheduled `loop.yml` runs. It fails unless there are at least three unique posts with passing checker provenance, unchanged content hashes and hosted-loop origins; the machine's counts match those posts; at least 48 hours have elapsed since the third initial post; and a hosted improver has actually adopted a changed `RULES.md` after a better score on at least three held-out cases. Initial `v1`, a proposed change, or a rejected trial cannot satisfy that gate. Every manual retry applies these checks.

Elapsed time alone is insufficient. The backup requires **at least six distinct completed scheduled loop runs after W1**, spanning **at least two Europe/Vilnius dates**. The first qualifying run must have been scheduled within six hours of W1, and the latest must have completed at least 48 hours after W1. A failed or rejected attempt remains evidence of unattended execution; canceled, queued or running jobs, manual dispatches, duplicate IDs, different workflows and manual reruns do not qualify. Safe evidence records contain only the qualifying IDs, public URLs, conclusions and timestamps, plus their actual count/date coverage. [GitHub workflow-run metadata and event filtering](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow).

GitHub supplies its temporary repository token only to the preflight and recording steps, with `actions: read` and `contents: read` permissions. The script sends it only to fixed `api.github.com` routes for this repository, never to Pages or the browser environment, and never persists raw API responses or the token. No model access, social credential or new external account is involved. [GitHub token permission syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), [read permission for workflow-run metadata](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow).

The recorder opens the real public [machine](https://xndanius.github.io/while-you-sleep/machine/) and [GitHub commit history](https://github.com/xndanius/while-you-sleep/commits/main), waits for their actual contents, and records the Chromium viewports. It shows the machine's statistics, recent runs and adopted rule change, then scrolls the public commit history. Two loaded-page recordings are trimmed to 18 and 12 seconds and joined. No page content, counter or history is substituted. The original WebM recordings are retained alongside the finished MP4 so the edits remain inspectable.

Only this workflow installs **Playwright 1.64.0**, the official 7 October 2026 release, into the ephemeral runner's temporary directory. The project's packages and other jobs stay unchanged. Chromium is installed with Playwright's matching browser/dependency installer. Both viewport and recording are explicitly 1920×1080; `recordVideo` is set to 30 fps and contexts are closed to flush their recordings. [Official pinned release](https://github.com/microsoft/playwright/releases/tag/v1.64.0), [browser installation](https://playwright.dev/docs/browsers), [recording and context closure](https://playwright.dev/docs/videos).

FFmpeg creates the MP4 using actual recorded frames, and ffprobe verifies **900 frames at 30 fps, exactly 30.000 seconds, 1920×1080**. A short or malformed capture fails the job; it is not padded into a successful backup. `backup-evidence.json` records capture times, the actual verified post count, W1 time, scheduled-loop coverage, adopted rule changes, public hosted-run and commit links, source-response hashes and the final MP4 SHA-256. [FFmpeg duration and frame limits](https://ffmpeg.org/ffmpeg.html), [ffprobe stream inspection](https://ffmpeg.org/ffprobe.html).

The run uploads one immutable artifact named `while-you-sleep-w3-backup-<run-id>-<attempt>`, containing the final MP4, evidence JSON and original WebM files, with **30-day retention**. The run summary links directly to its download. Danielius can also open **Actions → Record the W3 cloud backup → successful run → Artifacts** and download it while signed in. This backup workflow has read permissions only and does not commit, deploy, publish social posts or create a release. [Artifact retention and download URL behavior](https://github.com/actions/upload-artifact#retention-period), [GitHub artifact download instructions](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts).

`node scripts/record-backup.mjs --self-test` verifies the evidence and exact-duration rejection gates offline. `--preflight` checks the live evidence without opening a browser. `--record` repeats that preflight before capturing. The workflow is prepared before W1; recording runs only after its W3 evidence is present.
